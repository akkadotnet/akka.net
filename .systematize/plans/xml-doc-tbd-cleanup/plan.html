  • Document what a caller or maintainer needs: message/result meaning, relevant bounds, ownership, lifecycle, failure, cancellation, and backpressure where supported. Do not narrate the member name or promise unverified guarantees.
  • Preserve existing useful prose. No wholesale rewriting, formatting sweep, API renaming, new dependencies, warning suppression, or approval-baseline updates.
  • Check inherited targets recursively for useful documentation and cycles. Prefer inferred inheritance where unambiguous and supported; use a precise member cref when the source is ambiguous. Match parameter names and actual return/async behavior.
  • Do not turn real unresolved design work into descriptive prose. No such non-XML TBD was observed at this baseline; if discovered later, classify and retain it explicitly rather than silently deleting it.
  • Completion means no unresolved placeholder prose in the agreed source scope, accurate docs on all repaired contracts, and no behavioral/API changes. A count reduction alone is insufficient.

The meaningful smaller alternative is to complete only customer-facing and plugin-author APIs first, explicitly deferring implementation and test-support docs. It offers earlier IntelliSense value but does not fulfill “all TBDs.” The recommended full campaign keeps those later passes in scope.

Luna worker and orchestrator responsibilities

Authors: Luna agents draft all bounded documentation work. Assign non-overlapping files or member regions within a package; keep partial declarations, matching operator facades, and template/output pairs under coordinated ownership. Workers return prose changes, source evidence, verified inheritance targets, exact placeholder counts, and unresolved questions. Use isolated worktrees when editing independent packages; serialize any builds sharing outputs.

Adversarial reviewers: a separate agent reviews each authored portion without sharing the author’s reasoning transcript. Give it the diff, baseline, actual implementation/tests, and accepted documentation rules. It must look for false delivery/order/thread-safety/cancellation/backpressure/default claims; misleading parameter/return descriptions; unsafe inheritance or lost useful prose; inconsistent docs across related APIs; generated-source mistakes; and executable or nullable changes. Findings require a file/member, the disputed claim, and source evidence. “Looks good” without checking contracts is not sufficient. Authors correct findings; reviewers verify the corrections. Do not manufacture criticism to satisfy an adversarial label.

Accepted reviewer model: use Sol (gpt-6-sol) for independent adversarial review; the user explicitly approved this replacement for Terra. Authors use Luna (gpt-6-luna). Review findings require code evidence and corrected claims must be rechecked.

Orchestrator: integrate corrected portions into one package-sized PR, resolve shared contracts, inspect every inheritance/deletion choice, and own the combined checks and publication. Model agreement does not prove behavior. With three worker slots, use two Luna authors and one reviewer with the approved Sol reviewer, or finish an authoring wave and then review it; reviewer portions can be much smaller than the eventual PR.

Build-server use: worker drafts and local review checkpoints do not each become PRs or remote pushes. Complete semantic review and combine the batch before publication. Run the expensive integrated checks once per assembled candidate, and rerun only checks affected by later fixes. Default to one campaign PR consuming CI at a time while authors prepare the next independent batch locally. Draft status is not assumed to suppress CI. Keep all required checks and branch protections unchanged; reducing the number of published batches is the optimization.
